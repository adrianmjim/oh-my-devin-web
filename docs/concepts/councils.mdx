title: "Councils"
description: "Structured deliberation across independent seats: typed objections, consent-based closure, and a decision record that carries dissent."
---

A council puts a decision through structured deliberation before anyone builds
anything. You declare the seats once and run
`omd council run <council> "<question>"`. Independent seats examine a proposal
under distinct lenses, raise typed objections, and the deliberation closes by
consent — not by majority vote and not by a moderator's judgment.

## Declaring a council

Councils are always hand-authored. `omd setup` installs roles, skills, hooks,
and a default team, but no council — there is nothing to start from and nothing
to override.

A council lives at `.devin/councils/<name>.yaml`:

```yaml .devin/councils/design-council.yaml
name: design-council
seats:
  - role: security
    lens: threat-model
  - role: sre
    lens: operability
    contrarian: true
deliberation:
  rounds_cap: 3
  blocking_threshold: high
authority:
  on_consent: human
```

Each seat pairs a role from the catalog with a `lens` — the perspective it is
accountable for. A seat marked `proposer: true` drafts and revises the
proposal; a seat marked `contrarian: true` is framed to hunt for the strongest
counter-argument; an optional per-seat `model` diversifies the seats further.

## How a deliberation runs

The proposal comes from `--proposal <path>` (a free-form text file) or, absent
that, is drafted by the proposer seat. Each round then moves through fixed
phases: clarifications, typed objections, consent evaluation, and integration
of what was learned into the next revision. The loop ends at consent, at stable
dissent, or at the declared caps (`rounds_cap`, optional `wall_time_ms`).

Every seat runs as its own session in its own worktree. Moderation — relaying
arguments, validating objections, computing consent, deciding termination — is
deterministic orchestrator code, not a model seat.

<Note>
  A council is not a run. Unlike `omd run` and `omd team run`, `omd council run`
  creates no run id and no record under `.omd/runs/`, so it cannot be followed
  with `omd status`. Its output is the decision record, written when the
  deliberation closes.
</Note>

## Independence defenses

Deliberation only adds signal if the seats do not converge for the wrong
reasons:

- **Anonymized relay.** Arguments cross seats without attribution.
- **Isolated initial positions.** Seats take their first position before
  seeing anyone else's.
- **Echo collapse.** Near-identical arguments merge into one, carrying an
  endorsement count instead of repeated weight.
- **Decorrelation levers.** Per-seat lenses, per-seat models, and a contrarian
  seat keep perspectives distinct.

## Objections and closure

An objection carries a severity — `low`, `medium`, `high`, or `critical` — and
blocks consent only if it is within the seat's lens and its severity reaches
the council's `blocking_threshold` (default `high`). The deliberation closes as
exactly one of:

| Closure | Meaning | Exit code |
| --------- | ---------------------------------------------- | --------- |
| `passed` | No blocking objection stands | `0` |
| `blocked` | Dissent is stable and blocking | `5` |
| `bankrupt` | The rounds or wall-time cap was reached | `6` |

## Authority and the bridge to a team

`authority.on_consent` decides what a pass is worth: `human` (the default)
escalates the passed proposal for a human signature; `proceed` lets it flow
onward.

`--then <team>` bridges an authorized pass straight into that team's pipeline,
with the decided proposal as the pipeline's requirements. The bridge fires only
when the closure is `passed` and the decision is authorized:

| `on_consent` | Closure | Bridges with `--then` |
| ------------ | --------- | ------------------------------- |
| `human` | `passed` | Only together with `--sign` |
| `proceed` | `passed` | Yes, no signature needed |
| either | `blocked` or `bankrupt` | Never |

<Warning>
  `--sign` is an assertion by whoever runs the command. Nothing verifies that a
  human actually signed off.
</Warning>

The team named by `--then` is loaded and validated before the deliberation
starts, so a malformed team fails the command immediately — even in a run whose
closure would never have reached the bridge.

## The decision record

Every closure — passed, blocked, or bankrupt — writes a durable
`decision.json` under `.omd/deliberations/<question-slug>-<timestamp>/`: the
question, the proposal and its source, the consent result, the authority
applied, supporting arguments with endorsement counts, the complete objection
ledger, assumptions, and the conditions under which the decision should be
reconsidered. Dissent is always carried; nothing in a council declaration can
suppress it.

The command does not print where the record landed, so that path is how you
find it. See [Runtime files](/docs/reference/runtime-files).
