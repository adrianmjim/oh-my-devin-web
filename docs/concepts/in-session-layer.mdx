Oh My Devin has two lanes. The contractual lane is the `omd` CLI itself — runs,
teams, councils, each with enforced contracts and verifiable outcomes. The
conversational lane is the ordinary interactive Devin session you already work
in. The in-session layer is the bridge: a set of files installed into the
project that lets a live session delegate work to the contractual lane and hold
itself to a declared mode of working.

Nothing in the layer runs on its own. It is configuration the Devin session
reads, plus one hook script the engine invokes.

## What omd setup installs

A full project-level install writes eighteen paths across five components.

| Component | Files |
| --------- | ------------------------------------------------------------------ |
| `rules` | `AGENTS.md` — always-on rules at the project root |
| `roles` | The `architect`, `executor`, and `reviewer` roles under `.devin/agents/`, each with its schema under `.devin/schemas/` |
| `skills` | Eight `SKILL.md` files under `.devin/skills/` |
| `hooks` | `.devin/hooks/omd-mode.mjs` and the registry at `.devin/hooks.v1.json` |
| `teams` | `.devin/teams/default.yaml` |

The three installed roles form the pipeline the default team declares:
`architect` writes `architecture.json`, `executor` writes `evidence.json`, and
`reviewer` writes `review.json`, each validated against its own schema and each
allowed to write only that one file.

Setup is non-destructive and safe to re-run. See
[Layer installation](/docs/concepts/layer-installation) for install levels,
ownership regions, and what each outcome means.

## Delegation

The `omd-delegate` skill is the hinge between the lanes. The session launches a
role detached, polls its status, and reports what the snapshot carries — never
the role session's own conversation. That is what keeps the two lanes isolated
while still letting you follow the work.

## Session hooks

The `hooks` component registers exactly three events, each running the same
script with a different phase argument.

| Event | Phase | What the script does |
| ------------------ | -------------- | ---------------------------------------- |
| `SessionStart` | `session-start` | Injects the active mode's context |
| `UserPromptSubmit` | `user-prompt` | Injects the active mode's context |
| `Stop` | `stop` | Holds the session open until the mode's criteria are met |

At project level the registry is `.devin/hooks.v1.json` and the command is the
relative `node .devin/hooks/omd-mode.mjs`, so the engine must run hooks with the
project as the working directory. At user level the registry is the `hooks` key
of `~/.config/devin/config.json`, and the command carries the absolute,
shell-quoted script path.

Registration is per event and non-destructive: hook entries the layer does not
own are left in place, and events it does not claim are untouched.

## Persistent mode state

`omd mode set <mode>` records the active mode in `.omd/mode.json`;
`omd mode clear` removes it. There is no command to read it back — the hook
script is the reader.

On `SessionStart` and `UserPromptSubmit`, the script injects `Active mode:
<mode>` followed by that mode's context sentence. With no mode set, it injects
only that the layer is active.

On `Stop`, it blocks the session while the active mode still has unmet
verification criteria, naming them in the reason it returns. With no mode set,
it approves the stop.

| Mode | Stops when |
| ----------- | ------------------------------------------------------------------ |
| `team` | A pipeline terminal outcome is reported |
| `autopilot` | A pipeline terminal outcome is reported |
| `ralph` | The validate-repair loop reaches a valid artifact or a classified failure |
| `plan` | A plan artifact is produced |
| `verify` | Verification evidence is recorded |

`deep-dive` is the one mode without persistent state: it is a skill only, and
`omd mode set deep-dive` is rejected.

<Note>
  The hook script reads `.omd/mode.json` by a relative path, so the state it
  finds depends on the session's working directory. A session started outside
  the project root sees no mode.
</Note>

## Distributing the layer

`omd plugin build` packages the rules and skills half of the layer as an
installable Devin plugin — the user-level, cross-project alternative to
installing into each project.
