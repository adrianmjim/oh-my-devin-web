`omd` keeps its runtime state under `.omd/` in the project root. The directory
is transient orchestrator state, not project content.

<Tip>
  Add `.omd/` to your `.gitignore`.
</Tip>

```text
.omd/
├── runs/
│   └── <run-id>/
│       ├── events.jsonl             Progress journal, one event per line
│       ├── liveness.json            Heartbeat stamp
│       ├── stdout.log               Detached runs only
│       └── stderr.log               Detached runs only
├── mode.json                        Persistent mode state
├── deliberations/
│   └── <question-slug>-<timestamp>/
│       └── decision.json            One record per council closure
├── worktrees/
│   └── <instance>/                  Transient per-stage / per-seat checkouts
└── plugin/                          Default output of omd plugin build
```

All JSON that `omd` serializes uses camelCase field names. YAML that you
author — roles, teams, councils — uses snake_case keys.

`omd setup` writes nothing here: the in-session layer lives in `AGENTS.md` and
`.devin/`.

## Run records

`omd run` and `omd team run` each create `.omd/runs/<run-id>/`. An attached run
writes the journal and the liveness stamp; a detached run adds the two log
files its background process writes to.

`events.jsonl` holds one JSON object per line, each with a `type` and a
`timestamp`. The nine event types are `runLaunched`, `turnCompleted`,
`artifactValidated`, `repairAttempted`, `stageStarted`, `stageCompleted`,
`gateWaitEntered`, `gateWaitResolved`, and `terminalOutcome`. Unparseable lines
are skipped rather than failing a read.

`liveness.json` is a single stamp, rewritten every 15 seconds while a run is
live:

```json .omd/runs/<run-id>/liveness.json
{
  "stampedAt": 1785100931204
}
```

A run whose stamp is more than 120 seconds old reports as `stalled`. See
[Runs](/docs/concepts/runs) for how the states are derived.

<Note>
  The outcome report is printed, not stored. For a detached run it survives
  only in that run's `stdout.log`.
</Note>

## mode.json

Written by `omd mode set`, removed by `omd mode clear`, read by the installed
session hooks on every prompt:

```json .omd/mode.json
{
  "mode": "team",
  "context": "team mode active: run the declared team through the fixed three-stage pipeline.",
  "verification": ["pipeline terminal outcome reported"]
}
```

## decision.json

Every council closure writes one decision record under
`.omd/deliberations/<id>/`, where `<id>` is a slug of the question plus a
timestamp. Its fields:

- `question` — the deliberated question.
- `proposal` and `proposalSource` — the final proposal text and whether it was
  `attached` or drafted by the `proposer` seat.
- `consent` — the closure: `passed`, `blocked`, or `bankrupt`.
- `authorityApplied` — the authority policy that governed the closure.
- `supportingArguments` — each with `id`, `claim`, and an `endorsements`
  count from echo collapse.
- `objections` — the complete ledger: `seat`, `domain`, `severity`,
  `concern`. Dissent is always carried, including below-threshold objections.
- `assumptions` — what the decision rests on.
- `reconsiderWhen` — conditions under which the decision should be reopened.
- `humanDecisionRequired` — whether the closure escalated to a human.

The CLI never reads `decision.json` back. It is a terminal artifact, for you and
for other tools. The command does not print where it landed, so the path above
is how you find it.

## Worktrees

Team stages and council seats each run in a dedicated git worktree under
`.omd/worktrees/`, checked out detached from the repository's `HEAD`. The
directory is named after the stage (`architect`, `executor`, `reviewer`) or the
seat (`seat-<id>`).

Cleanup differs by caller. A team stage removes its own worktree as it
finishes. Council seats share one worktree per seat for the whole deliberation,
all removed together when it closes.

For the `executor` stage only, `omd` stages the worktree's changes to capture
the diff before teardown, which writes that worktree's git index.

<Note>
  Because these are real git worktrees, git also keeps administrative metadata
  under `.git/worktrees/` — inside the project but outside `.omd/`. Removing
  the worktree cleans it up.
</Note>

## Outside the project

Two things are written outside the project directory:

- **Temporary bundles.** Per-invocation compiled contract bundles and doctor
  probes go to the operating system's temporary directory (`omd-bundle-*`,
  `omd-doctor-*`) and are removed when the command finishes. A killed process
  can leak one.
- **The user-level layer.** `omd setup --level=user` installs into
  `${XDG_CONFIG_HOME:-~/.config}/devin`. See
  [Layer installation](/docs/concepts/layer-installation).
