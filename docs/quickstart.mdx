---
title: "Quickstart"
description: "Install the in-session layer into a project, check the runtime contract, and run your first role."
---

This walkthrough takes an existing project from zero to a completed single-role
run. It assumes you have [installed omd](/docs/installation).

<Steps>
  <Step title="Install the in-session layer">
    From the root of a project that is a git repository:

    ```bash
    omd setup
    ```

    `omd setup` writes the in-session layer into the project: an `AGENTS.md`
    rules file, the `architect`, `executor`, and `reviewer` roles with their
    output schemas, the delegation and installation skills, six mode skills,
    the default team, and the session hooks. It then reports every path it
    touched, grouped by outcome:

    ```text
    Created:
      AGENTS.md
      .devin/agents/architect/AGENT.md
      .devin/schemas/architecture.schema.json
      .devin/agents/executor/AGENT.md
      .devin/schemas/evidence.schema.json
      .devin/agents/reviewer/AGENT.md
      .devin/schemas/review.schema.json
      .devin/skills/omd-delegate/SKILL.md
      .devin/skills/omd-install/SKILL.md
      .devin/skills/autopilot/SKILL.md
      .devin/skills/ralph/SKILL.md
      .devin/skills/team/SKILL.md
      .devin/skills/plan/SKILL.md
      .devin/skills/verify/SKILL.md
      .devin/skills/deep-dive/SKILL.md
      .devin/hooks/omd-mode.mjs
      .devin/teams/default.yaml
      .devin/hooks.v1.json
    ```

    <Note>
      Setup is non-destructive and safe to re-run. It maintains its own marked
      region inside each file it owns; content you write outside that region is
      preserved, and a region you have edited yourself is reported as
      `Preserved` rather than overwritten. See
      [Layer installation](/docs/concepts/layer-installation) for the full
      model.
    </Note>
  </Step>
  <Step title="Check the runtime contract">
    ```bash
    omd doctor
    ```

    Every line should read `[pass]`. A `[warn]` on `devin-version` means your
    Devin CLI differs from [the pinned version](/docs/installation) — runs
    still work, but behavior is only verified against the pin.
  </Step>
  <Step title="Inspect the role catalog">
    ```bash
    omd roles list
    ```

    The catalog now contains the three roles installed by setup — `architect`,
    `executor`, and `reviewer`. Print one role's expanded contract — engine,
    model, tools, permissions, artifact, schema, and budget:

    ```bash
    omd roles show reviewer
    ```
  </Step>
  <Step title="Run the role">
    ```bash
    omd run reviewer "Review the pending changes and record your verdict"
    ```

    `omd` announces the run id, compiles the role's contract, opens a headless
    Devin session, lets it work within its budget, validates the artifact the
    role must produce — `review.json`, against
    `.devin/schemas/review.schema.json` — and reports the outcome:

    ```text
    omd run — launched (run 6f2b1c74-8d3e-4a19-9c05-1f7ab2e40d88)
    omd run — success
    run:      6f2b1c74-8d3e-4a19-9c05-1f7ab2e40d88
    role:     reviewer
    task:     Review the pending changes and record your verdict
    engine:   devin
    session:  devin-4471
    artifact: review.json (valid)
    turns:    2/6
    walltime: 41208ms
    outcome: success
    ```

    <Note>
      Runs execute against the real Devin CLI and spend Devin quota.
    </Note>
  </Step>
  <Step title="Read the result">
    The role's only writable path is its declared artifact, so the outcome of
    the run is the validated `review.json`. Add `--json` to any supporting
    command or to the run itself for a machine-readable report.
  </Step>
</Steps>

<Tip>
  `omd` keeps its runtime state — run records, mode state, decision records,
  worktrees — under `.omd/` in the project root. Add `.omd/` to your
  `.gitignore`.
</Tip>
